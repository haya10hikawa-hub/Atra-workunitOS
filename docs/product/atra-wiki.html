00

Atra とは

散らばった情報を「何を達成するための作業か」でまとめ、中断した作業に戻る瞬間だけに出てくる Raycast 拡張。

一文で

作業を再開するとき、前回の自分が何をしていて何を決めたかを組み立て直す時間を、Atra が消す。

仕事に必要な情報は複数のツールに分かれている。コード管理に PR が、チャットに会話が、カレンダーに期限が、ドキュメントに背景がある。これらは「どのアプリから来たか」で並んでいて、「何の作業のためか」ではまとまっていない。

だから作業を再開するたびに、複数のツールを開いて「前回どこまで進めたか・何が未解決か・次に何をするか」を組み立て直すことになる。Atra が減らすのは、この組み立て直す手間だけ。

この Wiki は応募書類（LEADING EDGE 四国／人財育成コース）の続きです。課題認識とペインは応募書類に記載済みのため繰り返しません。この Wiki が扱うのは、そこに書かれていなかった「で、実際どこで使うのか」です。
01

どこに座るのか

ここが応募書類に書かれていなかった部分です。Atra は既存ツールの置き換えではなく、既存ツールの上に乗る層でもありません。作業と作業の「あいだ」に座ります。

作業の1サイクル

①作業が発生する（Slack にメンション、PR にレビュー依頼、課題が届く）既存ツール
②中断する（授業／MTG／移動／就寝）—
空白 — 数時間 〜 数日
④再開する★ Atra
⑤作業する（エディタ・ブラウザ・Slack で）既存ツール
⑥終える／また中断する—
position

Atra は ④ の瞬間にしかいない。⑤ には入り込まない。

この1行から、設計が全部決まる

問い答え④ から導かれる理由
なぜランチャーなのかRaycast 拡張④ の瞬間に呼び出されるのはランチャーだから。専用アプリを開く動作自体が ④ の邪魔になる
なぜ実行しないのか送信・実行は持たない実行は ⑤ の仕事。Atra は ⑤ に入らないと決めたから
なぜ Slack を置き換えないのか読むだけ・書かない① を持たないから。情報が生まれる場所は既存ツールのまま
なぜタスク管理ではないのか一覧を作るのが目的ではない③ の空白を埋めるのが仕事。タスクを並べるのは ① 側の道具の仕事
Atra を見ている時間は1回およそ 30秒④ は瞬間だから。常駐しない・通知しない・ダッシュボードを持たない
言い換え。Atra は「情報をどこに置くか」を解く道具ではありません。情報はもう全部ある。Atra が解くのは「情報はあるのに、なぜ再開に手間がかかるのか」です。
02

使う場面

④ が実際にいつ起きるか。神山まるごと高専で1年をやっている2人の、実際の1日から。

場面1 — 朝、机に座った瞬間

寮から出て教室に着く。昨日の続きをやろうとするが、どこまでやったか思い出せない。ブラウザ履歴を遡り、PR を開き、Slack を遡る。手が動き始めるまで15分。

場面2 — 授業のあいだの30分

次の授業まで30分ある。何か進めたいが、立ち上げに10分かかると分かっているので始めない。30分がまるごと消える。ここが一番損をしている場面で、しかも自覚しにくい。

場面3 — 「あれどうなった？」と聞かれたとき

Slack で聞かれる。3日前に触った作業で、何を決めてどこで止めたか思い出せない。調べ直してから返信する。

共通していること

3つとも「情報が無い」場面ではありません。情報は全部ある。どこにあるか、どれが今の自分に関係あるかが思い出せないだけです。だから検索では解けません——検索するには、探す語を思い出している必要があるからです。

03

用語

この Wiki で使う言葉は4つだけです。以降これ以外の名前は出てきません。

言葉意味応募書類との対応
作業単位1つの作業のまとまり。PR・スレッド・タブ・ファイル・メモが入っている箱応募書類の「作業単位（WorkUnit）」と同じもの
再開ブリーフ作業単位を選んだとき右に出る「前回の自分からの引き継ぎ」新しい言葉
中断メモ作業を止めるときに残す1行新しい言葉
判断記録「これはこうすると決めた」を残したもの。消えない応募書類の「人間が最終判断する」の記録面
使わない言葉。WorkUnit OS / Launcher / Graph / Action Field / Node / Candidate。これらは凍結した V0 実装の語彙で、現在の製品方向ではありません。日本語の「作業単位」という考え方だけを引き継ぎます。

05

作業単位はどう作られるか

「で、作業単位ってどうやってできるの？」——応募書類の 難所②「似ている作業をまとめること」 がここです。応募書類には「今は重要度の近さで見ているだけで、内容が似ているかまでは判断できていない」と書きました。その先の答えを置きます。

大原則

人間が park した単位が、そのまま作業単位になる。機械は順番しか決めない。

やること
人間作業を止めるとき park を押す。そのとき開いていたものが1つの箱に入る。これが唯一の生成経路。違っていたら画面6で訂正する
機械① park のとき入れ先の候補を出す（直近に park した箱、同じディレクトリ／リポジトリを含む箱を上位に）
② 画面1の並び順を決める（最終 park 時刻＋時間帯＋訂正履歴）

なぜ機械に箱を作らせないのか

機械が箱まで作ると、外れたときに「探す場所」そのものが消えます。箱の境界を人間が持っていれば、推薦が全部外れた日でも作業は止まらない。

それに、この形なら2人で作れます。箱を当てる機械（応募書類の難所②）はまだ作れない。順番を当てる機械なら作れる。まず順番から作り、訂正の履歴が溜まってから箱の推定に進みます。

06

ルール

守らないと「思い出せる」が壊れるもの。

  1. 作業単位を確定させるのは人間。AI は候補を出すだけ。勝手に分類されると、外れたときに探す場所が消える
  2. 勝手に閉じない・消さない・アーカイブしない。1回消されたら二度と信用されない
  3. 判断記録は上書きしない。積む。前回どう決めたかが消えると、調べ直しが復活する
  4. 分からないことは埋めずに残す。応募書類と同じ原則。でっち上げた1行が混ざると全部が読めなくなる
  5. 本文は外に出さない。出るのはメタ情報だけ。自分たちの Slack・学校の課題・採用の話が入る
  6. まとめ方が全部外れていても、検索で辿り着ける。推薦が外れた日に作業が止まってはいけない
  7. 中断5秒・再開2秒を超えたら機能を削る。重い記録作業は必ず続かない
  8. 画面1の1行に4項目以上を出さない。読む時間が増えた時点で目的に反する
07

既存ツールとの境界

「① と ⑤ には入らない」という 01 の位置から、境界は自動的に決まります。

ツール担当する層Atra との関係
Slack / GitHub / Gmail / カレンダー① 情報が生まれるAtra は読むだけ・書かない。置き換えない
Notion / Linear人が手で登録した予定登録しなかったものを Atra が拾う。競合しない
Glean / 検索探す検索は探す語を思い出している必要がある。Atra は思い出せない状態が対象
ChatGPT / Copilot / Cursor⑤ 作業中Atra は ④ にしかいない。作業中は助けない
Zapier などの自動化実行の肩代わりAtra は実行しない。判断を渡す設計を最初から避ける

作らないもの

  • 自動実行・自動送信
  • チーム共有・権限管理
  • Web ダッシュボード・常駐画面・通知
  • 専用の作業画面（⑤ に入らないと決めたため）
08

申込書から変えたこと

応募書類を読んだ人が差分を追えるように、変えた3点を明記します。すべて 01 の「④ にしかいない」から出た帰結です。

作業画面
応募書類左に作業の流れ、右に作業面。8項目を表示する専用画面を作る
現在作らない。既存ツールに戻す
理由：⑤ に入らないと決めたため。作業画面を作ると Atra が作業中に常駐することになり、「④ の瞬間だけ」という位置と矛盾する。8項目のうち再開に必要なものは再開ブリーフ（画面2）に移した。
形態
応募書類第3段階でデスクトップアプリにする
現在Raycast 拡張
理由：④ の瞬間に呼び出されるのはランチャー。専用アプリを開く動作そのものが ④ の邪魔になる。加えて、UI を自分たちで作らない分の時間をまとめ方の精度に回せる。
並び順
応募書類重要度の順に表示する
現在再開する確率が高い順
理由：応募書類の難所①——「良い候補かどうかは正解データが存在しない」——を正面から解かずに済ませるため。重要度は測れないが、最終 park 時刻・時間帯・訂正履歴は測れる。測れるものだけで並べる。
変えていないこと。作業単位という考え方、AI は候補まで・人間が最終判断、分からないことは埋めずに残す、外部への送信と実行を仕組みとして無効にする——応募書類の原則はすべてそのままです。
09

現在地とこれから

構成

RaycastList / Detail / Action Panel — フロントは作らずに借りる
拡張（TypeScript）
ローカルストア作業単位 / 中身 / 中断メモ / 判断記録 — Mac の中から出ない
メタ情報のみ（本文は送らない）
Atra Core ← 自分たちが作るのはここ入れ先候補の生成 / 再開順のランキング（訂正履歴で学習）/ 時間の二軸モデル / 判断記録の保管

差別化

  1. 時間を2軸で持つ。情報が「いつ起きたか」と「自分がいつ知ったか」を分けて記録するので、再開時に「中断した時点の自分はどこまで知っていたか」を復元できる。
  2. 人間の判断が記録として残る。前回決めたことも、まとめ方の訂正も、上書きされずに積み上がる。

この2点は凍結した V0 で作った考え方を持ち込んでいます。持ち込むのは考え方だけで、V0 の製品方向・語彙・コードは引き継ぎません。

進め方

  1. ～ 9月位置を決める（いまここ）④ にしかいないという位置と、park を唯一の生成経路とする設計を固定する。
  2. ～ 11月並び順を動かすRaycast 拡張として画面1〜4を動かし、自分たちの実作業で毎日使う。訂正履歴を溜め始める。中間報告会（11/28）でここまでを実演。
  3. ～ 1月まとめ方に進む溜まった訂正履歴を使って、park のときの入れ先推定（難所②）に着手する。最終報告会（1/30）で実演。

今は決めないこと

機能特化か体験特化かの定義は今決めません。暫定の言い方は——「今は"作業を再開する瞬間"に絞る。そのための機能としてまとめ方を作る。範囲は自分たちで使いながら確定させる」。

降りた特化は2つ。領域特化（ドメイン知識で勝てない）と職種特化＝エンジニア向け（AI エージェントに飲まれる）。
