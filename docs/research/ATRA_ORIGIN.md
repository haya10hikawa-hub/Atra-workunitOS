# Atra — 原点

## 目的

Atraの目的は、**AIに仕事を任せても、元の意図と実際の変更の対応を失わせないこと**である。

AIはコードを書ける。テストも実行できる。だが、作業の質を担保するには「何を意図したか」と「実際に何が行われたか」を後から照合できなければならない。

Atraは、その対応関係を一つの仕事単位として追跡する。

## Atraが保持する5つ

1. **今回の意図** — 何を達成し、何を変えてはいけないか
2. **誰に何を委譲したか** — 人間・AI・Agentの担当範囲
3. **何を変更したか** — Gitで追跡された実際の差分
4. **どの証拠が返ったか** — Test、CI、Review、Runtimeなどの検証結果
5. **意図のどこまで満たしたか** — 達成・未達・不明・逸脱

## 改善するワークフロー

```text
意図
→ AIへ委譲
→ コード変更
→ 証拠
→ 意図との照合
→ 人間が受理 / 修正
```

現在のCode Reviewは主に「変更されたコード」を読む。Atraは、**その変更が何の意図に対応し、どこが未達・余計・未検証か**を見せる。

旧Atraの「散らばった情報から今やるべき仕事を再構成する」能力は捨てず、上流で**意図を形成する機能**として使う。

## 最初の検証

最初はSoftware Engineeringに限定する。

**Prompt / Issueの意図 ↔ Gitの変更箇所 ↔ Test・CI等の証拠**を対応付け、「レビュー時間が減るか」「意図逸脱を早く発見できるか」を測る。

価値が出なければ、この仮説は捨てる。
